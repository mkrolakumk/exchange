Teraz dlaczego to jest antywzorzec:
 
A. Silent Resource Waste (Ciche Marnotrawstwo Sieci)
Aplikacja wykonuje zapytania HTTP do API w tle, gdy użytkownik przegląda inne sekcje (Portfel, Historia).
Przy milionach użytkowników, to generuje miliony niepotrzebnych zapytań, obciążając backend.
Koszty hostingu rosną bez powodu.
B. DOM Thrashing (Męczenie Przeglądarki)
Budowanie całej tabeli kursów (30 walut + canvas wykresu) tylko po to, by nadać jej display: none, to marnowanie baterii laptopa/telefonu.
Na starszych urządzeniach może to powodować zacięcia (lagi).
C. State Desync (Rozdwojenie Jaźni)
Stan Routera: "Jestem w Portfelu".
Stan Modułu: "Mam otwarty wykres USD".
Te stany są sprzeczne, ale kod próbuje je pogodzić, wykonując pracę dla obu.
D. Singleton State Pollution (Zaśmiecanie Pamięci)
Zmienne w prices.js zachowują się jak Singletony – raz ustawione, żyją do końca sesji.
Brak mechanizmu "czyszczenia" (cleanup) przy zmianie widoku.
 
Ważne żebyście pamiętali, że zmienne globalne (modularne) w JavaScript żyją do końca sesji. Jeśli nie sprzątamy po sobie, stan "wycieka" między widokami. W tym projekcie efekt jest subtelny (nie ma błędu w konsoli), ale kosztowny (niepotrzebne fetch w tle). Trzeba tutaj wprowadzić cykl życia albo renderować tylko potrzebny widok

11. Race condiction w wykresach 
Użytkownik klika "Tydzień" - loadChart wysyła fetch 1 (wolny, 2s).
Użytkownik szybko klika "Miesiąc" - loadChart wysyła fetch 2 (szybki, 0.5s).
Wraca fetch 2 -> Rysuje wykres miesięczny.
Wraca fetch 1 -> Nadpisuje wykres danymi tygodniowymi.

Wykres pokazuje teraz dane niezgodne z wybranym przyciskiem. Nie powoduje to crasha (dzięki zabezpieczeniom które macie, tzn if(!canvas) ), ale wprowadza użytkownika w błąd. Trzeba tu anulować poprzednie żądanie fetch (AbortController) przy zmianie parametrów wykresu + w innych miejscach też zastosować AbortController bo wele zapytań "wisi" w tle niepotrzebnie.

15. Masowe re-rendery w DOM
 
Aplikacja wykorzystuje antywzorzec polegający na całkowitym nadpisywaniu struktury HTML widoku przy każdej aktualizacji danych (np. zmiana kursu waluty), zamiast aktualizować tylko zmienione wartości. W price.js mamy
Plain Text
container.innerHTML = `...cała lista walut od nowa...`;
 
Konsekwencje Techniczne i Biznesowe:
Utrata Stanu Interfejsu (UX Blocker) - Nadpisanie innerHTML usuwa z pamięci wszystkie istniejące elementy DOM i tworzy nowe. Jeśli użytkownik jest w trakcie wpisywania frazy w pole "Szukaj waluty" i w tym momencie przyjdzie aktualizacja cen yo pole input zostanie usunięte i stworzone na nowo. W efekcie mamy utrata fokusu w polu tekstowym i przerwanie pisania. Aplikacja staje się "nieużywalna" podczas dynamicznych zmian danych.
Degradacja Wydajności (Performance): - Przeglądarka musi wykonać kosztowny proces: Parse HTML -> Destroy DOM -> Create DOM -> Recalculate Layout -> Repaint. Przy liście np. 50 walut i odświeżaniu co kilka sekund, obciążenie CPU drastycznie rośnie, co na urządzeniach mobilnych (PWA) prowadzi do szybkiego drenażu baterii i "klatkowania" interfejsu.
Wycieki Pamięci (Memory Leaks) - Jeśli do starych elementów (które właśnie usuwamy) były podpięte Event Listenery, a nie zostały jawnie usunięte (np. removeEventListener), przeglądarka może mieć problem z ich posprzątaniem (Garbage Collection), co prowadzi do wzrostu zużycia RAM w czasie używania aplikacji.
Także tutaj kolejny mocny przykład dlaczego używanie innerHTML to antyPattern.

19.  Global namespace pollution (brak nowoczesnego podejścia ES6) - o co chodzi:
 
Obecnie Wasza aplikacja to "zupa" zmiennych. W index.html ładujecie skrypty jeden pod drugim. Wszystkie funkcje i zmienne zdefiniowane w menu.js (np. function setupMenu()) lądują w jednym, wielkim worku zwanym Globalnym Obiektem (window).
Plik app.js może użyć setupMenu() nie dlatego, że ją zaimportował, ale dlatego, że "przypadkiem" menu.js załadował się wcześniej.
Dlaczego to niebezpieczne:
Konflikty nazw: Jeśli w balance.js stworzycie zmienną const data = ... i w prices.js też const data = ..., to (zależnie od tego, jak są zadeklarowane - var/let/const w globalnym scope) jedna nadpisze drugą lub aplikacja się wywali. W dużych projektach to koszmar.
Kruchość: Jeśli zamienicie kolejność linii w index.html (np. dacie app.js nad menu.js), cała aplikacja przestanie działać, bo app.js spróbuje użyć funkcji, która "jeszcze nie istnieje".
Brak jasnych zależności: Patrząc na plik app.js, nie wiecie, skąd pochodzą używane w nim funkcje. Musicie zgadywać lub szukać po całym projekcie.
Jak powinno być (ES Modules):
Każdy plik powinien jawnie mówić, czego potrzebuje i co udostępnia:
 
 
Plain Text
// menu.js
export function setupMenu() { ... }
// app.js
import { setupMenu } from './menu.js'; // Jasno widać, skąd to mamy!
setupMenu();
Dzięki temu kolejność ładowania w HTML przestaje mieć znaczenie (moduły same dbają o kolejność), a zmienne są zamknięte wewnątrz plików i nie "wyciekają" na zewnątrz.

33. db.js - brak error handlingu W IndexedDB błędy mogą wystąpić nie tylko na samym żądaniu (request.onerror), ale na całej transakcji (transaction.onerror).
Jeśli transakcja zostanie przerwana (np. dysk jest pełny, przeglądarka ubije proces, błąd spójności danych), a my nie nasłuchujemy na transaction.onerror to Promise może nigdy się nie rozwiązać albo rzucić błąd, którego nie złapiemy -> tutaj można użyć graceful degradation i wtedy zrobić fallback do localStorage
